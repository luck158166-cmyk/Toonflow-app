# AI 短剧自动生产软件：长期任务目标

制定日期：2026-11-07。本文根据用户最新要求增补 `docs/masterPlan.md`，用于让后续开发始终围绕最终成片推进。原开发总则中已经确定的安全、费用、数据和阶段汇报要求继续有效；本文件以用户最新明确的产品目标和界面选择为准。任何阶段完成、构建通过或安装包生成，都不等于本文的最终目标完成。

## 一、唯一产品目标

以用户的 [Toonflow-app fork](https://github.com/luck158166-cmyk/Toonflow-app) 为 Windows 宿主，复用其画布、Agent、媒体供应商、任务恢复、文件和 FFmpeg 能力；把 [Jellyfish](https://github.com/Forget-C/Jellyfish) 的项目、剧集、镜头、资产、候选确认、证据追溯和状态语义按设计移植到 TypeScript 生产层，重新建成一款统一的 **AI 短剧自动生产软件**。Jellyfish 后端不作为运行依赖，Toonflow 原有功能保留。

用户的主要入口是粘贴或导入小说章节；也支持已有剧本和故事梗概。用户设定题材、画风、角色、单集时长、画幅、运行模式和费用上限后，软件应自动完成故事理解、改编、分集、剧本、资产、分镜、提示词、图像与视频、配音、字幕、配乐、剪辑、质量检查和导出。默认交付为 9:16、1080×1920、H.264 视频与 AAC 音频的 MP4。支持同一故事连续多集生产、局部重做、暂停恢复、完整备份及成本追踪。

最终形态是一款给短剧创作者使用的完整桌面产品：普通用户从项目列表进入生产工作台，能看见原文依据、分集、角色/场景/道具资产、分镜、生产队列、成本和成片；高级用户可以进入原有画布精修。不能把原版 Toonflow 换皮、若干孤立按钮或技术演示称作交付。

## 二、不可偏离的产品原则

1. **结果优先。** 所有开发任务都要能说明它改善了“输入章节后，稳定产出合格成片”的哪一环。仅增加页面、模型适配器或数据库表而没有进入真实生产链，不算该环完成。
2. **降低抽卡。** 生成前优先解决原文理解、人物和道具状态、分镜可拍性、参考素材绑定、模型参数、对白时间与提示词质量；生成后定位失败镜头，局部修复。不能把无限重试当成自动化。
3. **一个生产真相源。** 小说证据、剧本版本、资产版本、镜头计划、任务、产物、质量报告及费用以本地 SQLite 为准；画布是可精修的视图，修改须经受控采用才写回生产数据。
4. **确定性编排。** 流程由可恢复的状态机推进；模型承担有结构、有校验的创作步骤。每一步保存输入、输出、模型与模板版本、费用和来源，能够审计、回滚、继续执行。
5. **先拦后花。** 任何付费任务提交前必须经过就绪、提示词、参考素材、幂等与预算检查。真实 API 的调用内容、次数和人民币上限仍须用户事先明确授权；默认用 Mock，未经授权费用保持 0。
6. **保护已成功产物。** 崩溃、断网、超时、重新合成、改字幕、修改背景音乐、进程重启都不得让已成功的图像、音频或视频重复付费生成。在途供应商任务先恢复或对账，状态未知时暂停。
7. **诚实标注质量。** 程序通过、媒体格式合规、自动质检通过和“可发布”是不同状态。缺真实素材、预算与实际验收证据时，不宣称生产级或无人值守已实现。
8. **尊重许可和来源。** 逐项目核对许可证、依赖和模型权重条款；吸收设计或在许可允许时移植代码，保留来源与第三方声明，不把来源不清的实现直接复制进可商用产品。

## 四、必须贯通的自动生产链

1. **输入与证据。** 支持 TXT、Markdown、DOCX、粘贴文本和结构化剧本。识别章节、段落、人物称谓与别名；原文有哈希和位置。长篇分块时保留跨章记忆，不能因截断上下文丢失关键设定。
2. **故事改编。** 提取事件、人物关系、时间地点、冲突与悬念；先形成改编策略和分集大纲，再写分场剧本。每项重要事实可以回到原文；添加、合并或改变情节有明确标记。检查人物动机、时序、单集节奏、钩子和对白可演性。
3. **资产建立。** 自动识别人物、场景、道具、服装、声音及其别名。道具识别不仅看名词，还看是否被持有、使用、交接、遗失、损坏或影响后续剧情；记录每次状态变化及原文证据。资产有稳定 ID、参考图、版本、适用章节/场次和锁定状态，同一个对象跨集复用，必要时产生明确的换装、年龄、损伤等变体。
4. **分镜与片段。** 从场次得到可拍摄的镜头计划，明确镜头目的、主体、景别、机位、构图、起止人物站位、视线与轴线、动作、台词、道具状态、首尾帧及预计时长。按目标模型限制把镜头组合成视频生成片段；高风险复杂动作拆分，不能把多个独立事件硬塞进一个提示词。
5. **提示词编译。** 用结构化镜头、锁定资产和前后镜上下文生成 Seedance/Seedream 对应模型版本的提示词及素材顺序。付费前静态检查漏角色、错道具、时长不足、台词改写、参考图缺失、前后状态冲突、参数非法、提示词过载和禁止项。保存每一版提示词与对应模型请求快照。
6. **媒体生成。** 火山方舟为默认模型平台，复用 Toonflow 供应商任务的提交、保存、轮询、恢复和落盘机制。图片、视频、配音按明确的任务归属和幂等键生成；可在预算内使用样片/低成本预览，正式生成只针对通过预检的片段。模型或接口升级前重新核对官方规则。
7. **音频、字幕与剪辑。** 台词按人物音色生成并缓存；旁白、音效和授权配乐按镜头时间线混音。识别或对齐真实音频，生成可编辑字幕，自动处理发音、停顿、响度及背景音乐避让。FFmpeg 生成最终 MP4，字幕或配乐调整只重新合成。
8. **闭环质检。** 技术检查包括画幅、编码、时长、黑屏、静音、文件损坏；内容检查包括人物跨镜头一致性、服装与道具状态、场景连贯性、动作和对白是否符合剧本、字幕与语音是否一致、画面违和与多余文字。每项结果附可定位的镜头、时间码、证据和置信度；仅对失败部分重做，连续失败或无法判断时暂停并报告。
9. **连续多集。** 上集结尾的人物关系、衣着、伤情、道具归属、场景状态和未解决事件写回系列记忆；下一集继承并校验。队列可暂停、恢复、取消、限流与对账；每集有独立成本、版本、质量报告和导出历史。

## 五、界面目标与实际使用路径

**界面以用户提供的第 1 张 Jellyfish 效果图为主参考。** 使用白色或浅色背景、清楚的留白、可读的文字层级、项目卡片和进度信息；按钮采用协调的实色填充和明确的主次状态，避免灰暗、低对比或只有描边的主操作。项目列表可搜索、筛选、排序、查看状态和预算；选中项目后进入生产工作台。第 2 张深色效果图不再作为主风格。

主工作台至少包含：原文与改编、剧本、角色/场景/道具资产、分镜与时间线、生成队列、费用、质检、成片及备份。界面显示真实生产数据、失败位置和下一步操作；不能用漂亮的虚构成片、假进度或无作用按钮替代功能。常用路径应让初学者只需完成导入、风格/时长/预算设置和启动；复杂设置可展开，原画布供精修使用。

## 六、自动化的边界和失败处理

“无人值守”指用户完成初始配置和真实费用授权后，系统能自行推进确定性步骤、检查、生成、局部修复和导出，并在停止条件出现时准确暂停与说明。它不等于保证模型每次按提示词表演，也不等于无限重试直至花完预算。

自动模式遇到下列情形须暂停相应任务：原文关键事实冲突、主角身份或道具归属不确定、资产锁冲突、模型审核拒绝、供应商任务状态未知、连续失败、质检无法确定是否合格、预算或用户设定的重试次数触顶。暂停不影响其他已就绪任务；已成功产物保留。用户可在生产工作台审核并只重做受影响的步骤。

“可发布”包括内容和权利检查：素材、声音、字体、配乐和小说使用权可追踪；成片无明显技术故障、剧情断裂、人物漂移、字幕或音频错配。软件可自动给出“达到发布候选条件”的报告，最终是否发布由用户确认；不得自动向平台上传，除非用户另行明确授权并完成平台规则适配。

## 七、验收办法：用成片而非功能清单证明完成

### 第一层：真实单集闭环

在 Windows 安装包中，仅通过重建后的界面导入一段实际小说或剧本，包含至少 2 名主要角色、3 个场景、关键道具和对白。实际生成 1 集 8–12 镜头的 9:16、1080×1920 MP4，有可辨认的角色和场景、配音/旁白、字幕与配乐。保存原文证据、资产版本、分镜、提示词、任务、费用和质量报告。真实付费调用只在用户批准的内容、次数和金额上限内执行，账本与平台用量对账。

### 第二层：稳定性与成本

执行 `docs/masterPlan.md` 第 19 节的故障场景，并扩展验证：重复提交只产生一个付费请求；程序退出后恢复在途任务；成功产物不重付费；修改一句对白只重做必要音频和合成；改字幕/BGM 只重新合成；超预算、连续失败和状态未知均停机或停任务。记录每次生成、合格片段、成片分钟数、一次通过率、重做次数和实际人民币成本，不用单次漂亮样片推断稳定性。

### 第三层：多集与内容质量

用连续章节生产至少 3 集，核对主角身份、服装阶段、场景和关键道具跨集状态，以及上一集悬念的续接。以固定评分表检查原文忠实度、叙事节奏、角色与道具一致性、画面缺陷、台词、字幕、声音及平台技术规格；严重问题为零，其他阈值在真实基准测试后写入项目配置。若需要频繁人工重写提示词或反复手工抽卡才成片，则“无人值守生产级”未通过。

### 第四层：可交付产品

干净 Windows 环境可安装、启动、创建项目、导入、生产、暂停恢复、精修、导出、备份与恢复；旧 Toonflow 画布和主要原有功能仍可用。界面按浅色工作台设计完成，关键操作可用。交付源码、安装包、使用与故障文档、第三方声明、验收报告和已知限制。

## 八、每阶段的执行和汇报方式

- 每次开工先读取本目标、`docs/masterPlan.md`、路线图和当前代码/验收记录；找出离真实章节成片最近的阻塞项。先补最短端到端链，再加深单点能力，避免长期只做基础设施。
- 每个阶段必须有可观察的输入、输出、失败路径和验证证据。报告写明：实际新增了什么、用户能从哪个界面使用、对最终成片解决了什么、如何验证、仍缺什么、真实调用次数与费用。
- 每阶段完成后按总则提交并汇报；总则要求的阶段确认只控制进入下一阶段，**不改变长期目标**。用户的新要求经确认后增补目标和路线图，保留历史决策。
- 研究新开源项目时先说清它补哪一项缺口、代码和许可证是否核实、会增加什么依赖；无直接收益的不接入。不要为了“先进”同时维护多套同功能后端或重复数据真相源。
- 不以下载了项目、页面像效果图、类型检查通过、Mock 视频能播放或安装包能启动作为最终完成声明。只有上述四层验收均有证据时，才报告目标完成。

## 九、当前真实起点

截至本文件制定时，用户 fork 的 `codex/production` 分支已有生产数据与成本底座、部分方舟视频适配、小说章节索引与剧本基础检查、浅色/深色生产工作台初版，以及本地 FFmpeg 和技术质量验证记录；**尚未完成小说到多集成片的自动流水线、生产级提示词与资产连续性、完整方舟供应商集成、真实预算内成片验收和最终界面**。界面方向现已改为第 1 张浅色参考图。继续开发时以当前代码和测试结果复核本段，不把历史文档当成实时状态。
